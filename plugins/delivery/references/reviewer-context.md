# Shared reviewer language and source integrity

Apply [the core contract](core.md), the selected lens and actual project/user
instructions. Lenses are perspectives, not automatically started agents.

For authoring, read the relevant glossary entries and the Language/Writing
sections of [conventions](conventions.md). Use the owner's domain terms exactly;
do not coin silent synonyms or rename code to match a preferred dialect. Propose
missing terms with a definition and a concrete referent. Resolve ambiguity that
changes the decision rather than hiding it. If the glossary is absent, do not
invent agreed definitions. Read the full curation guidance when creating/editing
it, not for an unrelated read-only query.

Questions use the vocabulary of the person who must answer them. Give a concrete
example; make ordinary engineering decisions within authorized scope rather than
turning every implementation choice into an owner question. Preserve stated
owner intent, what must survive, evidence, history and rejected alternatives.

An unchanged shared reference or glossary entry may be reused only while its
exact text and established unchanged source revision/hash remain in context.
Check the actual revision; a path, mtime, summary or phase name is insufficient.
If revision checks are unavailable, read the needed source again. After
compaction, lost context, changed source/package or new scope, reload the selected
skill/lens and relevant cited artifacts before relying on them. Do not assume a
system prompt preserves files or that all skill bodies are automatically visible.

For brownfield, verify existing code and routes. For no-code greenfield, state
the absence and keep future paths, interfaces and commands explicitly proposed.
Source inspection is not runtime or user evidence; planned tests are not passed
tests. A missing/failed critical gate stays visible. Read-only review does not
modify the target; return concrete findings and their consequences.
